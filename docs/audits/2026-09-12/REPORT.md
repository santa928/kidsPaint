# Kids Paint 再評価 — 3歳児・タブレット向け

評価日: 2026-09-12。対象: ローカルの `8f3d5470db243916678cf297c605861cb00447b3`。アプリのコードと本番は変更していない。追加したものは、この監査記録・再現用スクリプト・画像だけ。

**推奨は、既存プロダクトを土台に、描画処理の一部とUI/UXを作り直すこと。** React・TypeScript・Vite・Canvas 2D・静的配信の組み合わせを維持できる。全面新規開発が必要な構造的な問題は、今回の調査では見つからなかった。

残すべき価値は「開くとすぐ描ける」「指を動かすと色や形が現れる」「自由に試せる」「広い描画面」。改善の中心は、子どもが操作を理解できることと、思いがけない入力で作品が損なわれないこと。

## 判断の根拠

| 選択肢 | 評価 | 理由 |
|---|---|---|
| 既存に小さな見た目修正だけを加える | 不十分 | 指の入力、道具の状態、消去と復元、回転時の座標変換にも問題がある |
| 既存を使って主要体験を改修する | **推奨** | 問題が描画・状態管理・操作パネルにまとまっており、部位ごとに置き換えられる |
| 別プロジェクトで全面的に新規開発する | 現時点では不要 | 小規模な1画面のアプリで、移行が必要なバックエンドや複雑な依存がない。仕様の取りこぼしやPWA移行作業が増える |

実行時依存は React と React DOM。TS/TSX は8ファイル・計1,948行で、うち音が788行、Canvasが497行。ビルドと型検査は成功、Lintはエラー0・既存の警告1件だった。技術基盤を捨てる理由は弱く、現在の道具や音・スタンプを再利用できる。

新規開発を再検討する条件は、OS固有の描画機能が主目的になる、共同編集やクラウド同期へ大きく転換する、など現在と異なる要件が生じた場合。いまの目的では、その複雑さを引き受ける利点がない。

## 実画面で確認した流れ

| Step | 操作 | 状態 | 観測 |
|---|---|---|---|
| 1 | 開いて描き始める | 良好・UI改善余地 | 登録や説明画面なしで描ける。横向き1024×768では描画領域が1024×633で約82%を占める |
| 2 | 色を選び、指で描く | 基本動作良好・入力に不具合 | 線と点を描ける。複数タッチの再現テストでは、2つの接点を結ぶ意図しない線が入った |
| 3 | スタンプを選んで押す | 動作良好・分かりやすさに課題 | 選択後に押せる。選択肢の絵文字と実際の線画が異なり、パネルを閉じると選んだスタンプが見えない |

### Step 1 — 開いた画面

![横向きタブレットの初期画面](/Users/santa/Documents/kidsPaint/docs/audits/2026-09-12/01-tablet-landscape.png)

広いキャンバスは長所。一方、道具を選ぶための手がかりが「スタンプ」「けしゴム」「もどす」などの文字に偏っている。3歳の利用では文字が読めなくても成立する設計を前提にしたい。これは設計上の判断であり、実際の子どもの理解度を観察した結果ではない。

実測した操作領域は、色44×44 CSS px、背景56×36、スタンプ入口72×36、鉛筆40×36、音量32×35.5、背景色32×32。背景色はコードでも32×32と指定されている。主要操作は56〜64 CSS pxを初期案として、隣との余白も確保する。これは本プロダクト用の提案値。

W3Cの強化基準は44×44 CSS pxで、頻繁に使う操作や取り消しにくい操作などでは、さらに大きくすることを勧めている。44pxを満たせば3歳児に十分だと判断できるわけではない。[W3C SC 2.5.5（AAA）](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced)

### Step 2 — 複数の指が触れた場合

![2つの接点をつなぐ意図しない斜線](/Users/santa/Documents/kidsPaint/docs/audits/2026-09-12/chromium-multi-touch.png)

Chromiumのタッチ入力を使用。1本目を(200,250)に置き、2本目を(600,550)に追加し、1本目だけを(240,250)へ動かした。その間の点(420,400)にも不透明な画素が発生し、斜線が入った。実際のiPad上で手のひらを置いたテストではない。

原因は、描画中の状態と最後の座標を全ポインターで共有し、入力を開始した `pointerId` を識別していないこと。まず「描き始めた指を維持し、追加の接点で線が飛ばない」仕様を実装するのが適切。これは完全なパームリジェクションを保証するものではない。[Canvas.tsx](/Users/santa/Documents/kidsPaint/src/components/Canvas.tsx:162)

### Step 3 — スタンプ

![スタンプ選択画面](/Users/santa/Documents/kidsPaint/docs/audits/2026-09-12/02-stamp-picker.png)

![実際に押されたうさぎ](/Users/santa/Documents/kidsPaint/docs/audits/2026-09-12/03-rabbit-stamped.png)

ボタンの絵文字と実際の描画を同じ絵にそろえ、現在選んでいるスタンプを閉じた状態でも表示したい。線画そのものを捨てる必要はなく、実際のスタンプ描画をサムネイルにも使う方法がある。図形も、白抜きの「○」から塗りつぶした丸が出る差をそろえる。

### Step 4 — 消しゴムから鉛筆へ戻る

![鉛筆を押した後にも消しゴムとして動作](/Users/santa/Documents/kidsPaint/docs/audits/2026-09-12/04b-pencil-still-erases.png)

消しゴムを選ぶ→右上の鉛筆を押す→描画をなぞる、で線が消える。ChromiumとWebKitでも再現。鉛筆と消しゴムが同時に選択表示になる。

`handleSelectDrawMode` がスタンプモードだけを解除し、消しゴム状態を解除しない。道具を `brush / eraser / stamp` の単一状態に整理し、色や虹色の設定は別に保持すると、この矛盾を防ぎやすい。消しゴムの前後で虹色設定を保つ既存の体験は維持する。[App.tsx](/Users/santa/Documents/kidsPaint/src/App.tsx:172)

### Step 5 — 通常Undoと全消去

![WebKitで通常Undoを行い前の線が残った状態](/Users/santa/Documents/kidsPaint/docs/audits/2026-09-12/webkit-undo.png)

通常Undoは、線を1本描く→別の点を打つ→もどす、で点だけが消えた。Chromiumは描画画素数が2,972→3,032→2,972、WebKitは2,788→2,856→2,788と元に戻った。

![全消去後にUndoが無効になった状態](/Users/santa/Documents/kidsPaint/docs/audits/2026-09-12/webkit-clear.png)

800ms長押しの再現テストで全消去され、Undoも無効になった。実装の判定値は600ms。長押しという工夫はあるが、誤消去後に助ける仕組みがない。

「あたらしいかみ」で前の作品を残して新しい紙へ移る案を推奨する。全消去を残す場合も、少なくとも取り消せるようにする。アプリ内の長押しを厳しくするだけでは、作品の復元性は改善しない。[ControlBar.tsx](/Users/santa/Documents/kidsPaint/src/components/ControlBar.tsx:35)、[Canvas.tsx](/Users/santa/Documents/kidsPaint/src/components/Canvas.tsx:128)

### Step 6 — 回転

![回転前の丸](/Users/santa/Documents/kidsPaint/docs/audits/2026-09-12/webkit-before-rotation.png)

![回転後に縦長になった丸](/Users/santa/Documents/kidsPaint/docs/audits/2026-09-12/webkit-after-rotation.png)

Chromium/WebKitとも、丸の描画範囲が70×70から53×100に変化した。元画像を新しい画面サイズへ縦横別々に引き伸ばす処理が原因。作品の座標系と画面の座標系を分け、縦横比を維持して表示する。[Canvas.tsx](/Users/santa/Documents/kidsPaint/src/components/Canvas.tsx:60)

縦向きでは色パレットの内容幅556pxに対して表示幅491pxで、虹色が初期の見える範囲から外れた。基本の色と虹色に横スクロールを要求しない配置を推奨。タッチスクロールの可否自体は今回の検証では判定していない。

### Step 7 — 再開

![再読み込み後に作品がなくなった画面](/Users/santa/Documents/kidsPaint/docs/audits/2026-09-12/08-after-reload.png)

再読み込み後、Chromium/WebKitとも描画画素数が0になった。描画内容はメモリ内にしかなく、画像保存の操作もない。自動保存を最優先にし、保護者が画像を書き出せるようにしたい。ブラウザー保存にも削除・容量制約があるため、自動保存を永久保管と表現しない。

### Step 8 — 背景と音

![音量設定画面](/Users/santa/Documents/kidsPaint/docs/audits/2026-09-12/09-sound-settings.png)

![背景と音量のパネルが同時に開いた状態](/Users/santa/Documents/kidsPaint/docs/audits/2026-09-12/10-overlapping-panels.png)

設定パネルは同時に1つにし、開いた場所と対象が分かるようにする。子どもには大きな音のON/OFF、音量の細かな調整は保護者向けの場所へまとめる案が適切。背景色選択も32pxの小さな点を大きくしたい。

音のバリエーションは価値がある。現在の初期設定は音OFF、設定画面の音量は120%、上限200%。表示だけから実際の音圧や危険性は判定できない。今回、iPadでの音量・快適さ・遅延は評価していない。音量を一律に下げる判断もしていない。

## 改善の優先順位

| 優先 | 対応 | 子ども・保護者にとっての効果 |
|---|---|---|
| 最優先 | 入力中の指の識別、鉛筆／消しゴムの状態修正 | 意図しない線や消去を防ぐ |
| 最優先 | 自動保存、全消去の復元、新しい紙への安全な移動 | 間違えて触っても作品を失いにくくする |
| 高 | 回転時の縦横比維持 | 描いた絵の形を保つ |
| 高 | 絵で分かる大きな道具、見切れない色・虹色、選択状態の統一 | 文字を読まなくても選びやすくする |
| 中 | スタンプの絵の統一、線幅を線の見本で表示、保護者向け保存 | 選んだ結果を予想しやすくし、作品を残せる |
| 中 | PWA更新・キャッシュ所有範囲、最小の回帰テスト | 更新後も安定して遊べる状態へ近づける |

## UI/UXの推奨方向

世界観の提案は「画材箱と画用紙」。背景は静かな机、作品は大きな紙、色はクレヨン、道具は実物に近い絵、スタンプは押される絵そのもの、作品一覧は作品帳、と語彙をそろえる。

画面は、中央の大きな紙を基準にする。紙の外側の上下に、実寸から高さを確保した画材トレーを配置する。色は基本色と虹色を常に選べる状態にする。道具はクレヨン・スタンプ・消しゴム・戻す・新しい紙を絵で示す。保護者の保存・音量調整は一つの入口にまとめる。描画面と道具の間に安全余白を取り、縦向きではトレーを折り返してボタンの大きさを保つ。

選択は枠・位置・小さな拡大などで明確にし、今の道具・色・太さを同じ場所で確認できるようにする。線幅の見本は4/8/14pxの小さな黒点だけに依存せず、実際に描ける線の見本を見せる。タップだけでもはっきり跡が残る太さを、実機で試して決める。

演出は操作への短い反応にとどめ、絵を描く場所を覆わない。完成時は描いた作品が主役になる。子どもが自由に触って表現できること、作品を見返せることを重視する。この方向は、NAEYCが挙げる自由なタッチスクリーン探索や子どもの作品の記録という実践例とも整合する。[NAEYCの実践例](https://www.naeyc.org/resources/topics/technology-and-media/preschoolers-and-kindergartners)

装飾イラストが必要になれば画像生成も候補になるが、まず画材の見分けやすさと実際のスタンプとの一致を優先する。画像を新しくするだけでは入力・復元の問題は解決しない。

## 実装上の対応範囲

再利用するのは、React/TypeScript/Vite、1画面構成、色・スタンプの定義、Canvas 2Dの描画資産、音源と必要な音処理、PWAの配信先。新しいフレームワークやバックエンドは必要ない。

重点的に改修するのは、Canvasの入力と座標変換、作品保存・履歴、Appの道具状態、色／スタンプ／道具の操作パネル。表示側と作品の座標を分離し、入力処理を小さな単位で検証できるようにする。音のファイルが長いことだけを理由に、音処理まで一括して書き直さない。

コード点検で見つかった追加の注意点:

- Undoは毎回キャンバス全体のImageDataを最大20枚持つ。今回の横画面寸法では画素配列だけで約49.5MiB。現在の遅さは測定していないが、高DPI対応を足す際に単純に4倍へ増やさない設計が必要。[Canvas.tsx](/Users/santa/Documents/kidsPaint/src/components/Canvas.tsx:96)
- DPR=2でも描画ビットマップはCSS上の幅・高さと同じだった。高密度画面用の描画解像度と履歴のメモリを一緒に設計する。
- Service Workerのactivate処理は、自分の名前以外の全キャッシュを削除する。同一オリジンの別アプリへの影響を避けるため、Kids Paintが所有する名前に対象を絞る必要がある。実際に他アプリのキャッシュを消す試験はしていない。[sw.js](/Users/santa/Documents/kidsPaint/public/sw.js:13)
- キャッシュ名が固定で、オフライン時はindex.htmlへ戻る。バージョン更新とオフライン復帰を実測してから公開する。[sw.js](/Users/santa/Documents/kidsPaint/public/sw.js:1)
- 日本語UIに対してHTMLの言語指定がen。色や道具の選択状態も見た目中心で、aria-pressed等を改善できる。全消去はキーボード入力の経路がない。WCAG全体の適合監査はしていない。[index.html](/Users/santa/Documents/kidsPaint/index.html:2)
- 既存CIはビルド・公開が中心で、テストのスクリプトはなかった。今回再現した実際の不具合を捕まえる最小のテストから追加する。

## 改修する場合の順番と受け入れ条件案

1. 入力と道具状態を直す。鉛筆選択後に描ける、途中の追加接点で線が飛ばない、キャンセル後に描画が残らない状態をテストする。
2. 保存・全消去・回転を直す。前の絵に戻れること、再開時に復元できること、回転しても形と入力位置が一致することを先に確保する。
3. 上記の安定した描画処理に、タブレット向けの新UIを載せる。主要操作を大きくし、道具の絵と選択状態を統一する。
4. 実機iPadで指・複数接点・回転・PWA再開・音を検証し、保護者同席で子どもの使い方を観察する。公開はその結果を踏まえて別途行う。

| 確認項目 | 受け入れ条件案 |
|---|---|
| 操作 | 初回から描ける。色・道具の主要操作が文字だけに依存せず、必要な色が初期表示で見える |
| 作品保護 | 最新の保存済み描画が再読み込みで復元される。全消去／新しい紙から前の作品へ戻れる |
| 入力 | 2本目の接点が線を飛ばさない。描画開始から終了までの指を管理し、キャンセル後に音や線が継続しない |
| 回転 | 丸の縦横比を保ち、指の位置と線の位置が一致する |
| 保存失敗 | 保存が失敗しても現在のキャンバスを消さず、保護者が書き出しなどの対応を取れる |
| 子どもの観察 | 説明なしで色を変える・スタンプを押す・描画へ戻る流れを試し、迷いや保護者の介入を記録する。今回未実施 |

性能目標は提案値として、代表iPadで連続描画中のフレーム時間p95を16.7ms以内、保存による100ms以上の入力停止を起こさない、自動保存はストローク終了後1秒以内に完了、を初期の測定目標にする。これらは達成済みの値ではない。実際の端末で画質・保存頻度・メモリのバランスを評価する。

非対象の提案は、ログイン、クラウド共有、ランキング、課金、広告、生成AIによる絵の採点、強制的なお題や連続プレイ報酬。自由描画という現在の目的を維持するため、今回の改修に加える理由がない。
